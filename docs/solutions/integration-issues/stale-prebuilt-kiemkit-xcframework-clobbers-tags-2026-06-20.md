# Stale prebuilt KiemKit XCFramework silently clobbers note tags on open

## Problem

After a content-derivation contract change (line-start `#tag` now counts as a real
tag), the macOS SwiftUI app silently stripped `#project` tags from notes **on open** —
no edit required. The freshly-built `kiem` CLI derived the tag correctly from the
identical note body, so CLI and app disagreed. User-visible impact: **silent data loss
on read in dev builds** — merely viewing a note rewrote its persisted metadata using a
stale rule, dropping legitimate tags and bumping `modified_at` (which then propagates
through sync).

## Symptoms

- Opening a note containing `#project` in the app → the tag disappeared.
- `kiem tags` reported `project` count `0` (expected `2`).
- `kiem show <id>` confirmed the note **body still contained** `#project` — the source
  text was intact, only derived metadata was wrong.
- `modified_at` was bumped despite the user making **no edit** — just opening the note.
- The freshly-rebuilt CLI derived `[project]` correctly from the same body. **CLI and
  app disagreed on identical input.**

## What Didn't Work

- **"It's a logic bug in the new `extract_tags` rule."** False. The Rust source was
  correct: `cargo test` and the shared `fixtures/content-derivation.json` cases passed,
  and the CLI (built fresh from that source) derived `[project]`. If the rule were
  wrong, the CLI would have been wrong too.
- **"It's the in-progress U12 sidebar code."** False. The sidebar work didn't touch
  derivation. `kiem show` proved the body was intact and the tag *should* derive; the
  corruption was in persisted metadata, not display.
- The decisive observation: **CLI correct + app wrong, same body** rules out the source
  logic entirely. The only thing that differs between CLI and app is *which compiled
  copy of `kiem-core` each one runs*. That points at the artifact the app links, not the
  code.

## Solution

The app links a **prebuilt, gitignored** XCFramework (`apple/KiemKit/`) wrapping
`kiem-ffi` → `kiem-core`. `xcodebuild` does not regenerate it. Regenerate from current
sources, rebuild, re-verify:

```sh
# 1. Regenerate KiemKit from current kiem-ffi/kiem-core
apple/build-kiemkit.sh

# 2. Rebuild the app (now linking the fresh core)
xcodebuild -project apple/Kiem.xcodeproj -scheme Kiem build | xcsift

# 3. Re-verify: open a note containing #project → tag preserved (kiem tags shows project = 2)
```

`apple/build-kiemkit.sh` is the whole regeneration story — it runs `cargo swift package`
against `crates/kiem-ffi` and swaps the result into `apple/KiemKit`:

```sh
repo_root=$(cd "$(dirname "$0")/.." && pwd)
cd "$repo_root/crates/kiem-ffi"
export MACOSX_DEPLOYMENT_TARGET=14.0
cargo swift package --platforms macos --name KiemKit --accept-all --silent "$@"
rm -rf "$repo_root/apple/KiemKit"
mv KiemKit "$repo_root/apple/KiemKit"
```

The damage is amplified by the app's open path. In `apple/Kiem/Models/KiemModel.swift`,
the editor's change handler re-derives and **persists** metadata through the embedded
core:

```swift
/// Editor change → Rust (re-derives title/tags) → refresh metadata.
func editorTextDidChange() {
    guard let id = selectedNoteID else { return }
    report { try store.updateNote(id: id, body: editorText) }   // re-derives + persists
    refreshNotes()
    refreshSidebar()
}
```

Because selecting a note loads its body into `editorText` and the editor emits an
initial `editorTextDidChange`, **opening a note calls `store.updateNote(body:)`** — which
re-derives tags with the embedded (stale) core and writes them back. With a stale core
that write *clobbers* the tags. After regenerating KiemKit the embedded core matches the
source rule, so the re-derivation is idempotent and the bug disappears.

## Why This Works

- **Staleness is the root cause.** The app does not compile `kiem-core` — it links a
  prebuilt XCFramework in `apple/KiemKit/`, which is **gitignored** (generated by
  `apple/build-kiemkit.sh`). That binary was dated Jun 12, built before the Jun 20
  contract change, so the app's embedded core enforced the **old** rule (`#` at line
  start = heading, excluded), while the source, fixtures, and CLI all used the **new**
  rule.
- **`xcodebuild` can't catch it.** Xcode has no dependency edge from
  `crates/kiem-core/src/*.rs` to `apple/KiemKit/`. To Xcode, KiemKit is an opaque
  vendored binary; it reuses the cached one. Editing Rust source and rebuilding the app
  produces a binary that *still embeds the old core*. Only `cargo swift package` (via
  `build-kiemkit.sh`) rebuilds that artifact.
- **The CLI doesn't have this problem.** `kiem` is built fresh from source by `cargo`
  on every build, so it always reflects the current `kiem-core`. That's exactly why CLI
  and app diverged — and why the divergence was the tell.
- **Opening writes, so staleness corrupts on read.** `editorTextDidChange` fires on note
  selection and calls `updateNote(body:)`, which runs the embedded core's derivation and
  persists the result. A matched core makes this a harmless idempotent no-op; a *stale*
  core makes opening any note a destructive rewrite — silent data loss with zero user
  edits and a bumped `modified_at`.

## Prevention

This is the **same failure family** as the cross-language fixture-parity discipline
already documented in this repo (see Related Issues): a derivation rule lives in multiple
compiled artifacts, and any one of them can silently drift out of lockstep. The existing
rule "change Rust + Swift + fixtures together" must gain a third obligation.

**Durable rule:** *After ANY change to `kiem-core` (especially `content.rs` derivation
rules), regenerate KiemKit (`apple/build-kiemkit.sh`) before building or testing the app.
`xcodebuild` will not do it for you.* This belongs on the derivation-change checklist in
`kiem-app/CLAUDE.md` (alongside "edit Rust, edit Swift, edit fixtures").

Guardrails, in increasing strength:

1. **Build-time staleness check (cheapest, highest value).** Fail the app build when
   `apple/KiemKit/` is older than any `kiem-core`/`kiem-ffi` source. A pre-build
   run-script phase (or CI step):
   ```sh
   newest_src=$(find crates/kiem-core/src crates/kiem-ffi/src -name '*.rs' \
     -newer apple/KiemKit/Package.swift -print -quit)
   if [ -n "$newest_src" ]; then
     echo "error: KiemKit is stale (newer Rust source: $newest_src). Run apple/build-kiemkit.sh." >&2
     exit 1
   fi
   ```
   This turns today's silent-wrong-result into a loud build failure.
2. **CI gate.** Build KiemKit fresh in CI from the committed sources so the tested app
   always embeds the current core. Optionally embed the `kiem-core` source hash into the
   FFI as a `core_version()` accessor and assert at launch (or in a smoke test) that it
   matches the source tree.
3. **Single entry point.** Wrap "regen KiemKit + build app" in one `Makefile`/script
   target so contributors never run `xcodebuild` against a stale artifact by habit.

**Latent secondary issue — flag separately:** *Opening a note should not trigger a write
at all.* Even with a matched core, the open → `updateNote` write is wasteful (bumps
`modified_at`, churns sync/CRDT history) and — as this bug proved — turns any core
mismatch into data loss instead of a display glitch. Fix idea: guard
`editorTextDidChange` so it only persists on a genuine user edit — set a
`private var isLoadingNote` flag around the programmatic `editorText` assignment in
`loadSelectedNote()` and early-return while it's true, or skip `updateNote` when
`editorText` is unchanged from the last-loaded body. Then derivation only runs on real
edits, and a stale core can at worst show a wrong title in the editor — never silently
rewrite persisted, synced metadata on read.
